# ロードマップ

各フェーズに「ゴール（1文）」「含むもの」「完了条件（テストで確かめられる形）」を置く。完了条件を満たすまで次のフェーズに進まない。節番号は [design.md](design.md) を指す。

| フェーズ | ゴール |
|---|---|
| M1 土台 | 1つの定義から、公開範囲ごとの REST の口と OpenAPI が作られ、iam でユーザーを認証・認可できる |
| M2 gRPC とサービスアカウント | 同じ定義が gRPC でも出せ、internal・partner の呼び出し元を iam で確かめられる |
| M3 サイドカー | Go 以外のサービスが、マニフェストとサイドカーで同じ API を出せる |
| M4 GraphQL | 同じ定義が GraphQL でも出せ、フィールドごとの判定がまとめて行える |
| M5 イベント | Stream・Event が WebSocket・Webhook・SSE で出せる |
| M6 運用と拡張 | 契約の破壊的変更を CI で検出でき、必要なら SOAP を足す |

## M1 土台

**ゴール**：1つの定義から、公開範囲ごとの REST の口と OpenAPI が作られ、iam でユーザーを認証・認可できる。

### 含むもの

- 定義の DSL（Query・Command）とレジストリ（3章）
- マニフェストの書き出し・読み込み・検証（2.2、4.3）
- 共通の層：入力の検証、認証、認可、エラーの開示のルール（4.1、6章）
- 公開範囲ごとの listener とフィールドの絞り込み（4章）
- REST と OpenAPI 3.1 の生成（5章）
- ポートとアダプタ：インメモリ、iam（ユーザーのアクセストークン）
- CLI：`api gen`、`api check`
- CI：`go test`、govulncheck、staticcheck

### 完了条件

- [x] `min=partner` のフィールドが public の応答と `openapi/public.json` に出ないテストが通る
- [x] `Expose` の無い操作がどの口にも出ないテストが通る
- [x] public の口で、internal にだけ出した操作が 404 になるテストが通る
- [x] 4.3 の不正な定義を `api check` がすべて報告するテストが通る
- [ ] iam を起動した E2E で、ユーザーのトークンの検証と `authz:check` の許可・拒否が通る（今は iam の応答を真似たサーバーでのテストだけ。実際の iam を CI で起動する仕組みが要る）
- [x] マニフェストを書き出して読み直すと同じ API になる（往復のテスト）

## M2 gRPC とサービスアカウント

**ゴール**：同じ定義が gRPC でも出せ、internal・partner の呼び出し元を iam で確かめられる。

- .proto の生成と、生成コードを使わない gRPC サーバー（5.2）
- サービスアカウントの認証・判定（iam の ADR 0112 のリソースに向けたトークン。判定は iam#152 まではスコープで行う）
- 提携先ごとのレートリミット

### 完了条件

- [x] 同じ定義から生成した .proto で、別のクライアント（grpcurl など）から呼べる E2E が通る（`scripts/e2e-grpc.sh`、CI）
- [x] REST と gRPC で、同じ入力に同じ出力・同じ拒否が返るテストが通る（`runtime/grpc_test.go`）
- [x] iam を起動した E2E で、サービスアカウントのトークンの認証と、判定の許可・拒否が通る（`scripts/e2e-iam.sh`、CI。API キーは iam が管理 API 専用にしたので受けないことを確かめる。`authz:check` でサービスアカウントを判定するのは iam#152 の後）
- [x] public の口に internal 用のサービスアカウントのトークンを送ると拒むテストが通る（口ごとのリソース。`runtime/resource_test.go`、`scripts/e2e-iam.sh`）
- [x] 提携先ごとのレートリミットが、ほかの提携先に影響しないテストが通る（`runtime/ratelimit_test.go`）

## M3 サイドカー

**ゴール**：Go 以外のサービスが、マニフェストとサイドカーで同じ API を出せる。

- `api sidecar`：マニフェストを読み、本体へ HTTP（JSON）で渡す
- マニフェストを YAML で直接書く経路
- Go 以外（例：TypeScript）の本体での E2E

### 完了条件

- [ ] YAML で書いたマニフェストと、同じ内容を Go で書いた定義の書き出しが一致するテストが通る
- [ ] Go 以外の本体を置いた E2E で、ライブラリと同じ認証・認可・フィールドの絞り込みの結果になる
- [ ] 本体に届く要求に、認証済みの主体が載り、絞り込み前のフィールドが本体から漏れないテストが通る

## M4 GraphQL

- SDL の生成と実行。フィールドの公開範囲の絞り込み
- フィールド・一覧の判定をまとめる（iam#153 が前提）

### 完了条件

- [ ] `min=partner` のフィールドが public の SDL に無く、クエリしても拒まれるテストが通る
- [ ] N 件の一覧の判定で、iam への問い合わせが1回になるテストが通る
- [ ] REST と GraphQL で、同じ操作に同じ拒否が返るテストが通る

## M5 イベント

- Stream・Event の定義
- WebSocket、SSE（REST の Stream）、Webhook（署名・再送・配信先の登録）、AsyncAPI の生成

### 完了条件

- [ ] 1つの Event が、WebSocket・SSE・Webhook の各購読者に届く E2E が通る
- [ ] Webhook の署名を受け手が検証でき、失敗した配信が設定どおり再送されるテストが通る
- [ ] 配信先の登録・一覧・削除で、ほかの Org の配信先を扱えないテストが通る
- [ ] 購読中にトークンが失効すると、保証値以内に接続が切れるテストが通る

## M6 運用と拡張

- 契約の差分の検査（破壊的変更を CI で検出）
- トークンの対象の限定（iam の ADR 0112 で使えるようになったので M2 で前倒しした）
- SOAP / WSDL（必要になったら）

### 完了条件

- [ ] マニフェストの版付けと互換性のルールを ADR で決めている（design.md 7章の未決事項を閉じる）
- [ ] そのルールで、公開範囲ごとに次を破壊的変更として CI が検出するテストが通る：操作・フィールドの削除、必須の入力の追加、型の変更、公開範囲を狭めること（internal は検出しても失敗にしない）
- [x] iam を起動した E2E で、対象の違う API 向けのトークンを拒む（`scripts/e2e-iam.sh`）
