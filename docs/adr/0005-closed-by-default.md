# 0005. 公開範囲ごとに口と契約を分け、既定は公開しない

- 状態: 承認
- 日付: 2026-11-02
- 関連: [design.md](../design.md) 4章

## 背景

internal の操作やフィールドが public に漏れるのが最も避けたい事故。

## 決定

- 公開範囲ごとに別の listener と別の契約ファイルを作る。internal の操作は public の口に存在しない
- `Expose` を書かない操作はどこにも出ない。どの公開範囲に出す操作にも `Authz` か `Anonymous` が要る（2026-11-04 に public だけから全公開範囲に広げた。partner に `Authz` なしで出すと、どの提携先 Org からでも呼べてしまうため）
- フィールドは `min` で公開範囲を狭められる。公開範囲によって、エラーの詳しさ・レートリミット・契約の安定性も変える

## 結果

- 書き忘れは「出ない」側に倒れる
- 口が公開範囲の数だけ増え、ネットワークの設定（internal は社内網だけ、など）はホスト先が行う

## 検討した代替案

- 1つの口で、要求ごとに公開範囲を判定する：判定の誤りがそのまま漏洩になる
